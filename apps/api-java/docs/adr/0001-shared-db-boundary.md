# ADR-0001. 공유 DB 위에서의 경계 — 파일럿은 무엇을 소유하지 않는가

- 상태: 채택
- 일자: 2026-08-03

## 맥락

파일럿은 Nest 모놀리스와 **같은 MySQL 인스턴스, 같은 스키마**를 본다. 별도 DB 를 쓰지 않는 이유는
셋이다.

1. 시드 데이터가 148 파일 71,862 줄이고 전부 Prisma 에 결박돼 있다. 별도 DB 를 만들면 그걸
   Java 로 다시 써야 하는데, 그건 파일럿보다 큰 작업이다.
2. 골든 대조가 무의미해진다. 두 서버가 다른 데이터를 보면 응답이 다른 게 당연해서, diff 가
   "구현 차이"인지 "데이터 차이"인지 구분할 수 없다.
3. 파일럿의 목적이 "실제 시스템 위에서 증명"이다. 격리된 장난감 DB 위의 증명은 약하다.

대신 소유권 문제가 생긴다. `account` 테이블은 모놀리스가 만들고, 마이그레이션하고, 계속 쓴다.
파일럿에는 그 행의 구조를 바꿀 권한이 없다.

## 결정

**파일럿은 데이터를 공유하되 스키마를 소유하지 않는다.** 구체적으로:

### 1. 구조 변경 금지 — `ddl-auto=validate`

Hibernate 가 스키마를 만들거나 고치는 경로를 아예 막는다. `update` 는 물론 `create-drop` 도 쓰지
않는다. 엔티티가 실제 컬럼과 어긋나면 조용히 컬럼을 만드는 대신 기동이 실패해야 한다.

스키마 정본은 `libs/db/prisma/*.prisma` 이고, `apps/api/prisma/schema.prisma` 는 머지 결과물이라
그것조차 정본이 아니다(모노레포 `CLAUDE.md` 참고).

### 2. 파일럿이 낼 수 있는 마이그레이션은 세 종류뿐

Flyway 는 `flyway_schema_history_pilot` 이라는 **별도 이력 테이블**을 쓰고 `baseline-version: 170`
(현재 적용된 Prisma 마이그레이션 수)에서 시작한다. 허용 범위는:

| | 무엇 | 왜 허용되나 |
|---|---|---|
| V171 | 커버링 인덱스 추가 | 구조를 안 바꾸고 성능만 바꾼다. 롤백이 자명하다 |
| V172 | 파일럿 전용 신규 테이블 | 모놀리스가 모르는 테이블이라 충돌하지 않는다 |
| V173 | `account.papy_balance >= 0` CHECK 제약 | 아래 참조 |

기존 8개 테이블의 **컬럼 추가·타입 변경·인덱스 삭제는 금지**한다. `db:build` 가 Prisma 소스에서
스키마를 다시 만들 때 조용히 되돌아가고, 그러면 파일럿이 알 수 없는 방식으로 깨진다.

V173(CHECK)은 예외적으로 허용한다. 이건 구조가 아니라 **불변식**이고, 모놀리스의 정상 동작을
막지 않는다(잔액을 음수로 만드는 쓰기만 거부한다). 다만 이걸 넣는 순간 모놀리스의 기존 결함이
500 으로 드러날 수 있어, W4 에 넣고 그 전에 원장 정합성을 먼저 확인한다.

첫 커밋에서는 Flyway 를 **꺼 둔다**. 켜는 순간 공유 DB 에 이력 테이블을 만드는 쓰기가 발생하는데,
아직 낼 마이그레이션이 하나도 없어서 얻는 게 없다.

### 3. 모놀리스 소유 테이블은 읽기 전용 투영으로만 매핑

`account` 는 `AccountRef` 하나로만 매핑하고 `@Immutable` 을 붙인다. 캐시 컬럼
(`total_points`, `papy_balance`) 쓰기는 전부 조건부 네이티브 UPDATE 로 격리한다.

더티체킹으로 잔액을 깎으면 read-modify-write 가 되어 오버스펜드가 난다.
`UPDATE ... SET papy_balance = papy_balance - :n WHERE id = :id AND papy_balance >= :n` 의
affected-rows 판정이 "검사"와 "차감"을 한 문장으로 묶는 유일한 방법이다.

`hero_id` 는 매핑하지 않는다. 파일럿 범위 밖이고, 매핑하면 그 FK 대상까지 딸려 들어온다.

### 4. 파일럿 범위 밖 테이블은 `@Entity` 금지

`contentCentury` 산출에 필요한 7개 테이블(person, event 등)은 `JdbcClient` 로만 읽는다.
`@Entity` 로 올리면 그 엔티티의 관계를 타고 도메인 경계가 무한히 번진다. ArchUnit 규칙으로 강제한다.

### 5. 통제 못 하는 전제는 부팅 때마다 확인한다

이 파일럿의 멱등성은 애플리케이션 코드가 아니라 **DB 의 UNIQUE 제약 5종**에 걸려 있다.
"조회 후 없으면 INSERT" 는 동시 요청에서 반드시 뚫린다.

그런데 그 제약은 파일럿이 만든 게 아니다. 누군가 Prisma 쪽에서 인덱스를 지우면 파일럿은
이중 적립을 조용히 허용하게 된다. 그래서 `SchemaContractVerifier` 가 기동 시 5종의 존재를
확인하고 없으면 **기동을 실패시킨다**. 정확성의 근거가 사라지면 서버가 안 뜨는 편이 낫다.

## 결과

- 얻는 것: 실제 데이터 위의 증명, 골든 대조 가능, 시드 재작성 0
- 잃는 것: 스키마 자율성. 파일럿은 자기 모델을 자기가 정하지 못한다
- 남는 위험: **공존 기간 동안 모놀리스가 같은 `account` 행을 락 없이 만진다.** 파일럿이 자기
  경로에 행 잠금을 걸어도 Nest 경로가 그대로면 프로덕션 경합은 남는다. 이건 완화가 아니라
  수용이고, README 에도 적었다.
- 다른 세션에서 `npm run db:build` 를 돌려 Prisma 스키마가 바뀌면 `ddl-auto=validate` 가
  파일럿 기동을 막는다. 조용한 오작동 대신 시끄러운 실패를 택했다.
