# ADR-0002. DATETIME 존 규약 — 저장은 UTC, 업무상 "오늘" 은 KST

- 상태: 채택
- 일자: 2026-08-03
- 계기: 골든 대조 테스트가 16시간 오프셋을 잡아냈다

## 맥락

MySQL 의 `DATETIME` 에는 타임존 오프셋이 없다. 저장된 것은 벽시계 숫자뿐이고,
"이 숫자를 어느 존으로 읽을 것인가" 는 **전적으로 클라이언트 규약**이다. 규약이 어긋나면
데이터는 멀쩡한데 응답만 몇 시간씩 밀린다 — 그것도 조용히.

이 DB 에는 헷갈리기 좋은 신호가 여럿 있다.

| 신호 | 값 | 유혹 |
|---|---|---|
| MySQL 서버 `time_zone` | `+09:00` | "서버가 KST 니까 KST 로 읽어야지" |
| 컨테이너 `system_time_zone` | `KST` | 위와 같음 |
| 배포 대상 지역 | 한국 | 위와 같음 |
| 개발 머신 TZ | **PDT** | 로컬에서만 재현되는 버그의 온상 |

이 신호들을 따라 처음에 `connectionTimeZone=Asia/Seoul` 로 잡았다. 계획서도 그렇게 적혀 있었다.

## 실측

규약을 정한 것은 서버가 아니라 **기존 쓰기 주체인 Prisma** 였다.

| | 값 |
|---|---|
| DB 원본 (`DATE_FORMAT`, 드라이버 변환 없음) | `2026-07-20 07:21:56.727` |
| Nest 응답 (`golden/wallet-me.json`) | `2026-07-20T07:21:56.727Z` |

숫자가 그대로이고 `Z` 가 붙는다. 즉 **Prisma 는 저장된 벽시계를 UTC 로 읽고 쓴다.**
서버 `time_zone` 이 `+09:00` 인 것은 이 규약과 무관하다.

`Asia/Seoul` 로 읽으면 같은 행이 9시간 어긋난 instant 가 된다.

## 결정

두 축을 **분리해서** 다룬다. 하나로 뭉치려 한 것이 애초의 실수였다.

### 축 1 — 저장 해석: UTC

```yaml
spring.datasource.url: ...?connectionTimeZone=UTC
spring.jpa.properties.hibernate.jdbc.time_zone: UTC
```

Prisma 가 정한 규약을 따른다. 파일럿이 이 규약을 "고칠" 권한은 없다 — 같은 테이블에
모놀리스가 계속 쓰고 있고, 한쪽만 바꾸면 그 순간부터 두 구현이 다른 시각을 쓴다.

Testcontainers 는 일부러 서버 TZ 를 `+09:00` 으로 띄운다. 앱이 커넥션에서 UTC 를 선언하므로
서버 TZ 는 결과에 영향을 주지 않아야 하고, 그 사실 자체가 테스트된다.

### 축 2 — 업무상 "오늘": Asia/Seoul

일일 환전 한도가 리셋되는 경계는 저장 규약과 아무 상관이 없다. Nest 는
`new Date(y, m, d)` 로 **Node 프로세스의 로컬** 자정을 만들고, 프로덕션에서 그건 KST 자정이다.

`ClockConfig` 가 `Asia/Seoul` 시계를 빈으로 제공하고 `WalletQueryService.startOfToday()` 가
그걸 쓴다. JVM 기본 TZ 에 맡기지 않는 이유는 배포 환경이 UTC 면 경계가 9시간 밀리는데
그게 조용히 일어나기 때문이다.

시계를 빈으로 주입하는 부수 효과가 하나 더 있다. Nest 에서는 자정 경계 동작을
**원리적으로 테스트할 수 없었다** — `new Date()` 를 코드 안에서 직접 부르기 때문이다.
파일럿은 시계를 고정할 수 있어서 "23:59 에 환전하고 00:01 에 또 하면 한도가 리셋되는가" 를
물어볼 수 있다.

## 이걸 잡아낸 것

골든 대조 테스트다. 첫 실행에서 정확히 16시간 어긋났고, 내역은 다음 둘이 겹친 것이었다.

- **−9h**: 픽스처 덤프가 mysql2 에 `timezone: '+09:00'` 을 줘서 벽시계를 KST 로 해석
- **−7h**: 그 instant 를 다시 로컬 게터(PDT 머신)로 벽시계화

두 실수가 서로 다른 층에 있었는데도 하나의 숫자로 합쳐져 나왔다. 이런 건 눈으로 못 잡는다.

픽스처 덤프는 이제 `DATE_FORMAT(created_at, '%Y-%m-%d %H:%i:%s.%f')` 로 **존 변환을 한 번도
거치지 않고** 문자열을 받는다. 오프셋 없는 값에 존 변환을 거는 것 자체가 버그였다.

## 결과

- `/wallet/me` 라이브 대조 통과 — Nest 와 파일럿이 같은 토큰으로 바이트 동일 응답
- 남는 위험: 이 규약은 **Prisma 의 동작에서 역산한 것**이지 어디에도 문서화돼 있지 않다.
  Prisma 메이저 업그레이드에서 날짜 처리가 바뀌면 파일럿이 조용히 어긋난다.
  `live-parity.sh` 가 그걸 잡는 유일한 그물이다.
- `DIVERGENCES.md` 에는 적지 않는다. 이건 의도적 차이가 아니라 같아지기 위한 조건이다.
