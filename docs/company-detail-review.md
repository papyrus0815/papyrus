## 1. 발견 사항

### P1 — 지금 사용자에게 보이는 결함

#### F1. '개요' 한 필드를 세 화면이 서로 다른 형식으로 다룬다 — **확인됨**
- 상세 개요는 리치텍스트 편집기(`InlineRichText`)라 **HTML**로 저장한다.
- 목록은 같은 값을 **문자열 그대로** 렌더한다 (`companies-list.page.tsx:313-314`).
- 등록·수정 모달은 같은 값을 **평문 textarea '한 줄 소개'**로 편집한다 (`company-register-modal.tsx:137, 705`).
- 실측: 삼성전자 개요에 두 줄을 입력하자 DB에 `검토용 첫 줄<div>검토용 둘째 줄</div>`가 저장되고, **목록 행에 `<div>` 태그가 그대로 보였다**. 모달을 열면 같은 태그가 textarea에 들어가고, 저장하면 태그가 글자로 굳는다.
- 개념도 엇갈린다: 목록은 '한 줄 소개', 상세는 여러 단락 서술(마이크로소프트 개요는 이모지 소제목이 있는 여러 단락).
- **처방**: 개요는 리치텍스트를 정본으로 하고, 목록·사이드바·국가 대시보드는 **평문 추출 + 1줄 말줄임**으로 보여 준다. 모달에서는 '한 줄 소개' 칸을 빼거나(상세에서 작성), 읽기 전용 미리보기로 바꾼다. — 규모 S

#### F2. 저장·삭제 실패 메시지가 서버 JSON 원문으로 뜬다 — **확인됨**
- `companyApi`의 `request()`가 응답 본문을 통째로 `Error.message`에 넣는다 (`shared/api/company/index.ts:456`).
- 실측: 빈 제목 연혁 저장 시 응답은 `{"success":false,…,"error":{"message":"입력값을 확인해 주세요: title should not be empty",…}}`이고, 토스트는 `저장 실패: {"success":false,"timestamp":…`로 뜬다. 상세 삭제의 409(인물 경력이 걸린 기업)도 같다.
- `shared/lib/get-api-error-message.ts`는 axios 전용이라 이 fetch 래퍼에는 못 쓴다.
- **처방**: `request()`에서 Nest 오류 본문의 `error.message`(없으면 `message`)를 뽑아 던진다. — 규모 S

### P2 — 데이터 유실 위험·구조

#### F3. 저장이 직렬화되지 않아, 겹친 저장은 늦게 커밋된 쪽이 이긴다 — **개연**
- 배열 모듈(연혁·제품·주가·목표주가·전망·시설)은 편집마다 **배열 전체**를 PUT하고, 서버는 지우고 다시 만든다(`company.service.ts:193~358`).
- `useCompanyMutation`(`use-company-detail.ts:141`)은 요청을 순서대로 묶지 않는다. 편집1(제목)과 편집2(제목+날짜)가 거의 동시에 나가서 서버가 편집1을 나중에 커밋하면, 편집2의 날짜가 사라진다.
- **처방**: `useMutation({ scope: { id: \`company-${id}\` } })` — react-query 5.90의 내장 직렬 큐. 이전 백로그 M1(먼저 실패한 patch가 상태 표시에 안 뜸)도 이 큐에서 함께 정리된다. — 규모 S

#### F4. delete-and-recreate 저장 — 이제 잠복 결함 셋이 한 근원에 모여 있다 — **확인됨(잠복)**
1. **연혁의 사건 연결이 지워진다**: `CompanyHistory.eventId` 칸이 있지만 입력 DTO와 `createMany` 어디에도 없다(`company.service.ts:222`). 한 행이라도 연결되면, 그 기업 연혁을 다음에 편집할 때 연결이 조용히 사라진다. 현재 연결 0행.
2. **id가 저장 때마다 새로 발급된다**: 연혁·제품 행에 댓글·딥링크·외부 참조를 붙일 수 없다.
3. **손자 데이터 연쇄 삭제**: `CompanyFacilityLaw`·`CompanyFacilityHistory` cascade, `naval_vessels.built_at_facility_id` NULL화. 현재 모두 0행.
- **처방**: 입력 DTO에 선택 `id`를 받아 **일치하면 수정·없으면 생성·빠졌으면 삭제**하는 id 기준 대조(reconcile)로 바꾼다. 연혁부터. F5의 사건 연결과 F13의 댓글은 이게 먼저다. — 규모 L

#### F5. 연혁과 관련 사건이 두 개의 평행 타임라인이다 — **확인됨**
- 같은 사실이 두 곳에 따로 있다. 예: 가스프롬 '국영 가스 콘체른 가스프롬 출범'(1989)은 연혁 행이자 별도 사건이다.
- 반대로 이번에 만든 설립 사건 5건(현대전자산업 1983, 삼성전자공업 1969 …)은 관련 사건에만 있고 연혁 탭에는 없다. SK하이닉스 연혁은 2026년 3건뿐이라 '1983 –' 기업의 연혁이 2026년에서 시작한다.
- **처방(단계별)**: ① 연혁 탭에 관련 사건을 **읽기 전용 '사건' 노드**로 섞어 표시하고 사건으로 링크한다. 중복 판정은 같은 날짜와 비슷한 제목 기준으로 하고, F4 없이 가능하다. ② F4 이후 연혁 행 ↔ 사건 연결(`eventId`)을 노출해 중복을 하나로 합친다. — 규모 M

#### F6. 관련 사건을 기업 쪽에서 연결·해제할 수 없다 — **확인됨**
- 연결 API(`POST /events/:id/organizations`)는 사건 쪽에만 있다. 개요의 '관련 사건' 빈 상태 안내도 "사건 상세의 관련 조직에서 연결하라"고 사용자를 다른 화면으로 보낸다.
- **처방**: 개요 '관련 사건'에 **"사건 연결"** 피커(사건 서버 검색 + 역할 선택)와 행별 해제를 둔다. 서버는 기존 엔드포인트를 그대로 쓴다. — 규모 M
