# 사건 상세 — 데이터 기반 재설계 (그래프 이전에 정본부터)

작성일 2026-10-01 · 브랜치 `feature/service-manager-v2` · **설계 문서 — 미구현, 결정 대기**

> 출발 질문: **"사건 상세에서 가운데에 글들이 쭉 적혀 있는 게 좋은가? 여러 데이터를 그래프 등으로 보여 주고 싶다."**
> 방침(사용자): **미래지향적으로. 설계를 바꿔도 된다. 지금 편하다고 살짝 고치는 것은 안 된다.**

## 0. 한 줄 결론

상세가 글뿐인 것은 디자인 문제가 아니라 **숫자·단계·진영·장소의 정본이 본문 HTML 안에만 있기 때문**이다.
그래프는 결과물이다. 그래프를 먼저 그리면 글에서 숫자를 긁어 오거나(파싱), 제목에서 날짜를 뽑거나,
평면 enum으로 진영을 추정하는 **땜질**이 된다. 그래서 순서는 **정본 → 입력 경로 → 화면**이다.

**원칙**

1. 화면에 그리는 모든 값은 **정본 한 곳**에서 온다. 글은 그 정본을 *가리킨다*(사본 금지).
2. 새 모델은 **사건 전용으로 만들지 않는다.** 국가·인물·조직이 같은 모델을 쓸 수 있어야 한다.
3. 시점은 전부 **구조화 날짜**(era/year/month/day + precision)다. `DATETIME`은 AD1000+만 안전하다는 레포 규약을 새 모델에서 반복하지 않는다.
4. 수치에는 **출처가 필수**다. 출처 없는 사상자 수를 차트로 그리면 화면이 단정하는 꼴이 된다.
5. 화면은 **데이터가 있으면 뜨는 모듈**로 짠다(이미 `enabledModules`가 이 방식이다). 카테고리는 순서만 정한다.

## 3. 결정 사항

> 각 결정은 **선택지 → 권고 → 영향**. ★가 권고안이다.
> 9-23 설계(`docs/event-treaty-signatory-plan.md`)가 이미 정한 것 — **참여국 한 줄 = 이 사건에서 이 나라의 배역**, **조약은 `Treaty`가 정본이고 사건은 링크** — 은 뒤집지 않고 그 위에 쌓는다.

### D1. 진영(Side) — 전쟁 전용 모델과 참여국의 이중 정본

**현황.** 진영 데이터가 있는 5건 중 4건은 같은 나라가 **두 곳**에 있다
(보오전쟁: 진영 구성원 8 · 참여국 9 / 보불전쟁 7 · 8 / 크림 5 · 5 / 아편 2 · 2).
반대로 진영이 없는 사건 40건은 같은 사실을 `ALLY`/`ADVERSARY` 역할로 적어 두었다.
"누가 어느 편이었나"의 정본이 **세 갈래**(진영 구성원 · 참여국 역할 · 본문)다.

| 안 | 내용 | 평가 |
|---|---|---|
| A | 둘 다 유지(참여국=전 사건, 진영=전쟁만) | 이중 정본 영구화. 같은 나라를 두 번 입력. **기각** |
| B | 진영으로 참여국을 대체 | 9-23 설계 파기. 조약·정치 사건은 진영이 필요 없다. **기각** |
| ★C | **진영을 참여국 위의 층으로 일반화** | 아래 |

**★C — 진영은 참여자를 묶는 층이다.**

- `EventSide`(신규, 전쟁 전용 아님): `eventId · name · parentSideId(연합>국가>부대) · color · sortOrder · description`.
  조약 협상의 양측, 내전의 파벌, 선거의 진영까지 같은 모델.
- **참여 한 줄은 여전히 하나** — 참여국(`EventCountryRelation`)·참여 인물(`PersonEvent`)·참여 조직(`EventOrganizationRelation`)에 **`sideId?` + 가담/이탈 구조화 날짜 + 가담 사유**를 단다.
  `CountryInSide`가 하던 일(joinDate·withdrawDate·participation)이 참여국 행으로 흡수된다.
- 군사 고유 속성(`forces`·지휘관·배치 부대·무기)은 **진영의 군사 확장**으로 남긴다(`SideDeployedUnit`·`SideWeapon`는 FK만 `EventSide`로).
- 역할 enum에서 `ALLY`/`ADVERSARY`는 **진영으로 파생 가능한 값**이 된다 → 신규 입력 금지, 기존 81행(35+46)은 진영 생성으로 이관 후 폐기.
  `INITIATOR`·`TARGET`·`MEDIATOR`·`OBSERVER`·`VICTIM`·`BENEFICIARY`·`FOUNDED`·`DISSOLVED`는 진영과 직교하므로 유지.

**영향.** 마이그레이션 1: `belligerent_side`→`event_side`, `country_in_side` 10행 → 참여국 행에 `side_id` 병합(없는 나라는 참여국 행 생성), `ALLY/ADVERSARY` 40건은 사건별 진영 2개 자동 생성 후 **검수 큐**로(자동 판정은 '누구 편'을 모른다).
쓰기 단일 통로 `EventCountryParticipantService`(9-23)에 `sideId`를 3상 필드로 추가 — 자연키 머지 그대로.

### D2. 전개 단계 — 하위 사건인가, 날짜 달린 단락인가

**현황.** 단락 제목 날짜 63건, 하위 사건 보유 31건. 「12일 전쟁」은 하위 사건 0개인데 단락 5개가 사실상 단계(개전·상호공습·미국개입·휴전·후속)다.

| 안 | 내용 | 평가 |
|---|---|---|
| A | 단락에 구조화 기간 컬럼 추가 | 시간의 정본이 둘(하위 사건 · 단락). 단계에 참여국·수치·장소를 달 수 없다. **기각** |
| B | 별도 `EventPhase` 모델 | 하위 사건이 이미 계층·다중상위·연결사유·BC날짜를 다 가졌는데 같은 것을 또 만든다. **기각** |
| ★C | **단계 = 하위 사건, 단락은 하위 사건을 가리킨다** | 아래 |

**★C.**

- 시간이 있는 단계("미드나잇 해머 작전 2025-06-22")는 **하위 사건**이다. 그래야 단계에도 진영·수치·장소·인물이 붙고, 목록·타임라인·검색에 같은 것으로 나온다.
- `EventSection.subjectEventId?`(신규 FK) — "이 단락은 이 하위 사건을 서술한다". 배경·여파 같은 **주제 단락은 비워 둔다**.
- 전개 타임라인 = 하위 사건(정본)의 기간. 단락은 그 위에 앵커로 붙는다. 제목 문자열은 읽지 않는다.
- 목록 팽창 우려: 목록은 이미 계층 접힘·최상위 앵커·하위 접기(메모리: event-subevent-list-view-review)가 있어 흡수된다. 필요하면 하위 사건에 `granularity`(단계/사건) 표시만 둔다 — 별도 모델은 아니다.

**영향.** 스키마는 FK 1개. 63건의 단계 단락을 하위 사건으로 승격하는 것은 **데이터 큐레이션**(§5 추출 흐름)이다. 자동 변환하지 않는다.

### D3. 수치 — 측정값(Observation)과 출처(Citation)

**현황.** 수치가 있는 사건 104건, 구조화 사상자 5건(문자열). 출처 모델 없음.

| 안 | 내용 | 평가 |
|---|---|---|
| A | `casualties_data` 컬럼을 숫자로 바꾸기 | 사상자만 해결. 병력·미사일·비용·지수 종가는 또 컬럼 추가. **기각** |
| B | 사건 전용 `event_metric` | 국가·조직·진영 수치와 분리. 경제 사건이 계속 '하루 1사건'이 된다. **기각** |
| ★C | **범용 측정값 + 지표 카탈로그 + 출처** | 아래 |
| D | 국가 지표 테이블까지 전부 EAV로 통합 | 방향은 맞으나 지금 범위 초과 — C의 후속 |

**★C.**

```
MetricDefinition   지표 카탈로그 — key, 이름, 단위 종류(명·발·USD·%·pt…), 의미(사망=전사+전상사? 질병 포함?), 집계 규칙
Observation        측정값 한 줄
  subject          다형: event | eventSide | eventParticipant | country | historicalCountry | organization
  metricId         → MetricDefinition
  value            DECIMAL — 점 추정
  low / high       DECIMAL? — 범위 ('18,000~20,000')
  approx           Boolean — '약'
  qualifier        Text? — 정의상 단서 ('질병 사망 별도', '자결 포함')
  at / from~to     구조화 날짜 (era/year/month/day/precision) — 시점 또는 구간
  scopePlaceId?    → Place (D5) — '테헤란에서의 사망'
  sortOrder
Source             출처 — 종류(책·논문·기사·공식발표·데이터셋), 서지, URL, 발행일
Citation           다형 인용: target(observation | eventSection | eventParticipant | …) → source + 위치(쪽·절)
```

- **같은 지표에 출처별로 여러 값**을 허용한다(이란 사망자: 정부 627 · 서방 추정 1,000+). 화면은 범위로 그린다. 이게 역사 데이터의 실제 모양이다.
- `casualties_data` 10행 · `war_cost` 9건은 Observation으로 이관 후 컬럼 폐기.
- 국가 지표 테이블(`country_economic_indicator` 등)은 **이번엔 유지**하되 지표 키를 `MetricDefinition`과 맞춘다 → D안으로 가는 다리.
- 경제 사건 '나스닥 25,297 마감'류는 사건을 없애라는 것이 아니다 — **사건에 Observation을 단다**. 같은 지표의 점들이 모이면 상세에서 시계열이 그려진다.

**영향.** 신규 테이블 4개. 쓰기 경로는 3상·자연키 머지(9-23 규약). Citation은 이후 인물·국가 서술에도 쓴다(현재 출처 0).

### D4. 본문 — HTML 문자열에서 참조하는 문서로

**현황.** execCommand 에디터(메모리: god 5,683줄)가 만든 HTML을 `MEDIUMTEXT`로 저장. TipTap v3.18 PoC 완료(메모리: tiptap-migration-poc — 멘션·figure·표·리사이즈가 핵심 비용).

| 안 | 내용 | 평가 |
|---|---|---|
| A | HTML 유지 + `data-*` 속성 스팬으로 참조 | 에디터가 속성을 보존한다는 보장이 없고, 서버가 참조 무결성을 검사할 수 없다. **기각** |
| ★B | **TipTap JSON을 정본으로, 인라인 참조 노드** | 아래 |

**★B.**

- 본문 정본 = ProseMirror JSON. 인라인 노드: `entityRef(person|country|historicalCountry|event|organization|place)`, **`observationRef`**, `citationRef`.
- 글의 "약 627명"은 `observationRef`가 렌더한다 → 수치를 고치면 글도 바뀐다. 사본이 사라진다.
- 블록 노드: `chart(observation 질의)`, `timeline(하위 사건)`, `sideMap` — 모듈을 본문 중간에도 둘 수 있다.
- 서버가 JSON을 파싱해 **참조 색인 테이블**(어느 단락이 어느 엔티티·수치를 가리키나)을 쓰기 시점에 갱신 → 역참조('이 인물이 언급된 사건')가 질의 하나가 된다(메모리: person-biography-term-entity-review의 근인 해소).
- 기존 622단락 HTML → JSON 일괄 변환(PoC의 파서). 변환 불가 노드는 `rawHtml` 블록으로 보존하고 목록화.

**영향.** 가장 큰 공사. 에디터 교체와 같이 간다. D3 없이 B만 하면 참조할 수치가 없으므로 **D3 이후**.

### D5. 장소 — 지명사전(Place)

**현황.** `City`에 좌표 없음, 사건 `city_id` 0건, `location` 자유 문자열 85건. `Treaty.location`도 문자열.

| 안 | 내용 | 평가 |
|---|---|---|
| A | `City`에 lat/lng만 추가 | 전장·해협·시설(포르도 핵시설)은 도시가 아니다. **기각** |
| ★B | **`Place` 지명사전 + 사건-장소 링크(역할)** | 아래 |

**★B.**

- `Place`: 이름, 종류(도시·시설·전장·해역·지역…), 좌표(점) 또는 범위(bbox), `cityId?`/`administrativeDivisionId?` 연결, **시대별 이름**(`PlaceName`: 이름·언어·구조화 기간 — 콘스탄티노폴리스/이스탄불).
- `EventPlace`: 사건 × 장소 × 역할(전장·표적·서명지·발생지·회담장) × 순서.
- `Treaty.location`·`Event.location`·`Person` 출생지 텍스트는 단계적으로 Place로.
- 역사 국경(폴리곤)은 **범위 밖**. 점 지도까지만 이번 설계에 포함.

### D6. 인물 참여 역할 — 문장에서 구조로

**현황.** `person_event.role` 167행이 `'직함(기간) — 이 사건에서 한 일'` 문장.

- 앞부분(직함·기간)은 **재임 정본**(`GovernmentPositionTenure`)의 사본이다 → `tenureId?` FK로 가리킨다.
- 뒷부분은 **기능 분류**(결정권자·지휘관·협상대표·서명자·피해자·주도자…, 카탈로그)와 **서술**(`roleDescription`)로 나눈다.
- 진영 소속은 D1의 `sideId`.
- 쓰기는 지금 delete-recreate(9-23 §5가 지적한 비대칭) → 참여국과 같은 자연키 머지로 올린다.

### D7. 조약 — 9-23 결정 유지, 남은 구멍만

9-23 설계가 이미 정했다: **조약 = 문서(정본 `Treaty`), 사건 = 체결·비준·파기 행위, 둘은 `(조약, 사건, 자격)` 링크.** 바꿀 이유 없음. 남은 것:

- 링크 **0행** — 회담/조약 사건 43건과 조약 17건을 잇는 데이터 작업.

### D8. 국가가 아닌 행위자 — 이동기 고트·훈 (구현됨 2026-10-02)

**현황(실측).** 훈족은 DB에 없었고 고트족은 정착 뒤 왕국(서고트 418~·동고트 493~)으로만 있었다. 그래서

378년에 존재하지 않던 '동로마 제국' 1국). 민족 테이블은 1행.

**결정 — 세 층.**

| 층 | 무엇 | 모델 |

- 새 테이블이 아니라 종류 추가인 이유: 참여국·진영 구성원·인물 국적·재위·전환·종속·측정값 대상이 전부
  `HistoricalCountry`를 FK로 가리킨다. 별도 테이블이면 그 전부에 세 번째 FK가 필요하다. 전례도 있다(막부=REGIME, 메이지=PERIOD).

**구현.** 마이그 `20261002095834_historical_people_kind_and_membership_structured_dates`(백필 21·16행, 01-01 센티널 → 연 정밀도),

## 5. 데이터 유입 — 이게 없으면 또 5건에서 멈춘다

`belligerent_side`가 5건에서 멈춘 이유는 모델이 아니라 **입력 비용**이다. 정량 정보는 지금 104건의 글 속에 있다.

- **추출 → 검수 → 승격** 흐름: 단락 본문에서 후보(수치·단계·진영·장소)를 뽑아 *제안*으로 저장, 사람이 승인하면 정본에 쓰고 본문 해당 구절을 참조 노드로 치환.
- 후보는 정본이 아니다 — 별도 제안 테이블(상태: 제안·승인·기각, 근거 구절 오프셋).
- 시드 규약 갱신: 새 시드는 글이 아니라 **정본(하위 사건·진영·Observation+Source)부터** 넣고, 글은 그것을 참조한다.
