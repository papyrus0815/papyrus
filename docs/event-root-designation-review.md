# 사건 "최상위 지정" + "전체 하위 조망" 기능 검토

## 결론 먼저

지금 없는 것은 '깊이'가 아니라 **구분과 스코프**다. 실 DB의 최대 계층 깊이(3단)가 목록 API 캡(3단)과 정확히 같고 카탈로그가 `autoLoadAll`로 전량을 이미 받아오므로(`apps/web-admin/src/pages/events/list/events.page.tsx:301-308`, `apps/api/src/libs/event/presentation/event.controller.ts:587-614`), **서버 서브트리 API를 새로 만들어도 오늘 화면에 추가되는 사건은 0건**이다. 진짜 통증은 생존 루트 167개 중 147개(88%)가 자식 0인 단독 사건이라 '제1차 세계대전' 같은 앵커가 파묻히는 것, 그리고 앵커 하나로 모수를 좁힐 축이 없다는 것이다.

채택안은 **안 A″ — 파생 앵커 + 명시 오버라이드 + 클라 스코프**다. 안 A를 서버 없는 형태로 축소한 뒤(안 A′), **사용자 결정(2026-08-11)**에 따라 안 C의 명시 지정을 되살려 합친다 — 단 안 C 원안(백필 있는 `eventScale` enum)이 아니라 **파생 술어를 덮어쓰는 3상 오버라이드 1컬럼**으로. 안 C에서 지정 어포던스·어휘 규율·a11y 규약을, 안 B에서 `descendantCount` 정렬축·'단독' 토큰을 이식한다. 그리고 세 안이 모두 "쓰기 경로라 범위 밖"으로 뺀 **앵커 아래로 사건을 모으는 일괄 편입 도구**를 앞 배치로 끌어올린다 — 조망할 트리 자체가 아직 만들어지지 않고 있기 때문이다.

신규 지면 0, 신규 **조회** API 0. 스키마는 nullable enum **1컬럼(`anchorOverride`)뿐**이고 기본값 null이 곧 파생 판정이라 **백필이 없다**(안 C의 임계 3 백필 논쟁이 통째로 소멸한다). `rootEventId` 미러(안 B)·서브트리 조회 API(3안 공통)는 기각/**착수 트리거 조건부 백로그**로 내린다.

> ### 사용자 결정 (2026-08-11) — 아래 본문은 이 결정을 반영해 갱신됨
> 1. **'최상위 지정'의 의미 = (a) 구분·표시 + (b) 모으기 + (c) 빈 사건 선언 — 셋 다.** (c) 때문에 스키마 1컬럼이 되살아난다. 원 검토서의 "미해결 1"은 이것으로 종결.
> 2. **비루트 앵커 허용 — 라벨만 분리.** 루트만 '최상위 사건'이라 부르고, 비루트 앵커의 배지는 '하위 N건'으로 표기한다. 원 검토서의 "미해결 3" 종결.

## 지금 상태 (실측)

DB 실사는 `mysql://papyrus@localhost:3307/papyrus`(MySQL 8.0.45)에 읽기 전용 SELECT로 수행됐다. 수치는 전부 실행 결과다.

| 항목 | 값 | 근거 |
|---|---|---|
| event 총 행 / 생존 / 소프트삭제 | 323 / 275 / 48 | `SELECT COUNT(*), SUM(deleted_at IS NULL)…` |
| 생존 루트(`parent_event_id IS NULL`) / 비루트 | 167 / 108 | 동일 쿼리 |
| 깊이 분포(루트=0) | d0 **167** · d1 **103** · d2 **5** · d3+ **0** | 재귀 CTE 집계 |
| 실제 최대 깊이 | 3단(0-base 2) | 동일 |

| 자식을 가진 루트 / 자식 0 단독 루트 | **20 / 147 (88%)** | 루트별 child_cnt 집계 |
| 루트 자식 수 분포 | 0:147, 1:5, 2:3, 3:2, 4:2, 5:2, 7:1, 10:1, 11:3, 18:1 | 동일 |

| 손자를 가진 노드 | 2개('프랑스의 대러시아 차관' 4건, 엔비디아 계열 1건) | 동일 |
| 살아있는 추가 상위 엣지(`event_parent_link`) | **0** (전체 1행이나 자식·부모 양쪽 소프트삭제된 데모 잔재) | 조인 확인 |

| `event_relation` | 2행 | `COUNT(*)` |

| 성능 | 전체 트리 재귀 CTE 2ms, WW1 서브트리 1ms, `parent_event_id` FK 인덱스 존재 | `SHOW INDEX` + 타이밍 |

읽어야 할 함의 세 가지:

- **깊이는 문제가 아니다.** 증손자 0건, 손자 5건. "손자·증손자까지 조망"의 대상이 오늘 5건뿐이다.
- **로딩도 문제가 아니다.** 목록 캡(3단)과 실 데이터 최대 깊이(3단)가 같고 `autoLoadAll`이 켜져 있어, 브라우저 메모리에 생존 275건 전량과 완전한 계층이 이미 들어와 있다.
- **문제는 밀도다.** 167개 루트가 페이지 상한 100(`event.controller.ts:425`)을 넘고, 그중 88%가 앵커와 시각적으로 완전히 동등하다.

## 진짜 문제 (근인)

### 근인 1 — '최상위'가 개념이 아니라 부작용이다

루트 판정은 `ROOT_EVENT_WHERE = { parentEventId: null }` 하나뿐이고(`apps/api/src/libs/event/domain/event-hierarchy.ts:15`), 스키마에 앵커·규모·핀을 나타내는 컬럼이 없다(`libs/db/prisma/event.prisma:243-384` 전수 확인 — `is_top_level`·`root_event_id`·`depth`·`path` 전무). 그래서 '제1차 세계대전'과 '1914 킬 운하 확장 재개통'이 목록에서 같은 자격으로 나열되고(`event.controller.ts:518`), 화면 어휘의 '최상위'는 집계 라벨로만 존재한다(`catalog-header-stats.tsx:81`, `catalog-main-content.tsx:437`). 지정·전환을 뜻하는 버튼은 web-admin 전체에 0건이다.

**단, 사용자가 예로 든 WW1은 이미 루트다**(`parent_event_id IS NULL`, 자식 18). 즉 요청 ①은 "루트로 만들기"가 아니라 "앵커임을 구분·표시하기" 또는 "아래로 모으기"로 재해석되어야 한다 — 세 안 모두 이 검증을 건너뛰고 '해제 버튼 리네이밍'을 지정 기능이라 불렀다.

### 근인 2 — 조망의 결핍은 데이터가 아니라 스코프다

카탈로그는 필터를 서버에 보내지 않는다 — `useEvents`에 `pageSize`·`autoLoadAll`만 넘기고 카테고리·국가·세기는 클라에서 판정한다(`events.page.tsx:301-308`, `apps/web-admin/src/features/event-filters/model/useEventFilters.ts:303-330`). 그런데 그 모수의 입구가 `events.filter((event) => !event.parentEventId)`로 **루트 전량 고정**이라(`useEventFilters.ts:326-329`), '이 앵커 아래에서만'이라는 질의를 표현할 자리가 없다. URL에도 14개 축 중 parent/root/anchor 계열이 하나도 없다(`pages/events/list/lib/parse-catalog-search-params.ts:58-88, 157-185`).

즉 필요한 것은 서버 스코프 파라미터가 아니라 **클라 모수 축소 1축**이다. 이것이 안 B의 존재 이유(`GET /events?rootEventId=`)가 무너지는 지점이기도 하다.

### 근인 3 — 트리를 만드는 도구가 한 건씩만 동작한다

앵커 아래로 기존 사건을 모으는 유일한 경로는 상세 '하위 사건 추가' 모달에서 **한 건씩** 고르고, 이미 다른 부모가 있으면 confirm → 거절 시 '추가 상위로 연결' 제3선택을 거쳐, `childEventIds` **전체목록**을 PUT하는 것이다(`pages/events/detail/components/detail-network.tsx:246-300`, 서버는 detach-후-재부착: `apps/api/src/libs/event/application/event.service.ts:694-702`). 반대 방향인 '최상위로 올리기'는 hover에서만 드러나는 부정형 '해제' 버튼 하나뿐이다(`parent-block.tsx:128` + `detail-network.styles.ts:129-155`의 `$reveal` opacity 0).

결과가 데이터에 그대로 찍혀 있다 — 1914~1918년 생존 루트 6건 중 5건이 WW1에 붙지 않은 채 단발 루트로 흩어져 있다. **조망할 트리가 아직 안 만들어지고 있다**는 것이 88%의 정체다.

### 근인 4 — 계층 지면이 6개인데 각자 다른 것을 센다

LIST 행 트리 / TREE 위젯 / 요약 모달 `TreeView`(`widgets/event-list/ui/tree-view.tsx:25-66`) / 상세 children-block / 드로어 하위 프리뷰 / 타임라인 ↳ 접두. 카운트도 제각각이다 — `hiddenChildCount`·`visibleChildCount`는 직계만(`features/event-hierarchy/model/useEventHierarchy.ts:200, 276-297`), 트리 배지는 로드된 것만(`widgets/event-tree-view/ui/event-tree-view.tsx:722-734`), 서버 총계는 루트만(`event.controller.ts:746`, 라이브 167 vs 생존 275). 게다가 서버가 보내는 `extraParentCount`는 프론트 매핑 누락으로 소멸한다(`entities/event/model/eventTransformers.ts:103-165`).

그래서 어느 화면도 "이 아래 전부"를 정직하게 말할 근거가 없다. **일곱 번째 지면을 만드는 것은 이 근인의 악화다.**

## 검토한 3안과 판정

### 안 A — 스키마 0변경 · 재귀 서브트리 API + 기존 지면 앵커 모드
정합성 표면이 가장 작다(파생 상태 0, `ROOT_EVENT_WHERE` 소비 0). restore 가드에 `extraParentLinks` 정리를 포함해 INV-2를 지키는 유일한 안이고, 읽기 CTE 캡을 쓰기측 `CYCLE_MAX_DEPTH=50`(`event.service.ts:795-796`)에 맞춰 '저장은 되는데 조망만 잘리는' 창을 없앤 것도 이 안뿐이다. 그러나 ⑴ 비루트 앵커를 허용한다면서 모수를 `useEventFilters.ts:329`에 그대로 흘려 **백지 화면**을 만들고(오늘 손자를 가진 노드 2개가 전부 비루트라 정확히 이 경로를 밟는다), ⑵ 배치 순서가 자기 진단과 반대다("앵커만 칩이 오늘의 개선분"이라 써 놓고 그 칩이 배치5, 개선분 0이라 자인한 subtree API가 배치1).

### 안 B — `rootEventId`/`lineageDepth` 계보 미러
forest 증명(주 FK 부모 ≤1 + 순환 가드 + dangling 0 → 루트 유일)은 실제로 성립하고 쓰기 지점 열거도 grep 실측과 일치하는, 재료로서 가치 있는 산출물이다. 하지만 **존재 이유가 무너졌다** — `GET /events?rootEventId=`로 서버에서 필터를 조합하겠다는 것이 이 안의 핵심인데, 카탈로그는 필터를 서버에 보내지 않으므로 소비처가 0이다. 게다가 그 파라미터는 기술적으로도 성립하지 않는다(아래 fatal). 275행·최대 깊이 3·CTE 2ms에서 성능 근거가 0인데 DB가 강제하지 않는 파생 컬럼과 11개 쓰기 지점 훅을 영구 부채로 남긴다.

### 안 C — `EventScale` enum + `/events/anchor/:id` 전용 지면
셋 중 유일하게 '지정'을 능동형 1급 조작(⚑ 토글)으로 만들었고, ROOT_EVENT_WHERE 방어(별도 파일 + 금지 주석 + AND 결합 spec)가 가장 강하며, 미커밋 워킹트리를 회피하는 배치 구성도 가장 안전했다. 하지만 안 C만의 차별점이 적대 검증에서 전부 깎였다 — 백필 임계 3은 자식 있는 루트 20건 중 8건(보불전쟁·1차 아편전쟁·보오전쟁 포함)을 탈락시키고, 신규 라우트는 계층 지면을 6→8개로 늘리면서 a11y를 새 지면에만 넣겠다고 명시하며, 기본 착지인 개요 탭은 모수 19행짜리 통계 대시보드다(WW1은 자식 18 전원이 잎이라 깊이 히스토그램이 영원히 막대 1개).

## 채택안 — 안 A″ (파생 앵커 + 명시 오버라이드 + 클라 스코프)

### 스키마 — nullable enum 1컬럼, 백필 없음

사용자 결정 (c)("자식이 아직 없는 사건도 미리 앵커로 선언")는 파생 술어로 **표현이 원리적으로 불가능**하다. 따라서 컬럼 하나를 추가하되, 안 C 원안처럼 앵커 여부를 *저장*하지 않고 **파생 판정을 덮어쓰는 오버라이드**로만 둔다.

```prisma
// libs/db/prisma/event.prisma — enum 신설
/// '최상위(앵커) 사건' 판정 오버라이드. null = 자동(자손 ≥ 1이면 앵커).
/// 앵커 여부를 저장하는 컬럼이 아니라 *파생 판정을 덮어쓰는* 컬럼이다 —
/// 그래서 기존 20건에 대한 백필이 없고, 자식이 붙거나 떨어져도 자동 추종한다.
enum EventAnchorOverride {
  /// 자손이 0이어도 최상위(앵커) 사건으로 취급
  ANCHOR
  /// 자손이 있어도 앵커로 취급하지 않음 (예: 엔비디아 계열 자손 1)
  PLAIN
}

model Event {
  // ...
  anchorOverride EventAnchorOverride? @map("anchor_override")
}
```

판정 단일식: **`isAnchor = anchorOverride === 'ANCHOR' || (anchorOverride !== 'PLAIN' && descendantCount >= 1)`**

| `anchorOverride` | 자손 ≥ 1 | 자손 0 | 오늘 해당 |
|---|---|---|---|
| `null` (기본) | 앵커 (자동) | 일반 | **전 323행** |
| `ANCHOR` | 앵커 | **앵커 (빈 앵커 — 결정 (c))** | 0 |
| `PLAIN` | **일반 (강등)** | 일반 | 0 |

이 형태를 택한 이유:
- **백필 0.** 전 행이 `null`로 시작하고 파생이 기존 앵커 20건을 그대로 잡는다. 안 C가 걸렸던 "임계 3이면 보불전쟁·1차 아편전쟁·보오전쟁이 탈락" 문제가 발생 자체를 안 한다.
- **자동 추종.** 자식을 붙이거나 떼면 앵커 여부가 저절로 따라온다. 저장형 플래그였다면 배치2(일괄 편입)마다 플래그 갱신 훅이 필요했다 — 안 B가 무너진 것과 같은 종류의 부채다.
- **강등도 된다.** `PLAIN`이 있어 '엔비디아 호퍼 → 블랙웰' 같은 자손 1짜리 잡음을 손으로 뺄 수 있다. 파생 단독안에는 없던 탈출구다.
- 계층 쓰기 경로(`parentEventId`·`EventParentLink`·순환 BFS·tx)를 **전혀 건드리지 않는** 독립 스칼라라, INV-1/2/3과 `ROOT_EVENT_WHERE`에 영향이 0이다.

마이그레이션: `ts-node libs/db/prisma/run-migrate.ts add_event_anchor_override` (소스 파일 수정 후 실행 — `apps/api/prisma/schema.prisma` 직접 수정 금지). 이어서 DTO 변경분에 `npm run build:nestia`.

### API
**배치0~3은 서버 0변경.** 배치4의 독립 결함 3건만 서버를 건드리며, 그것들은 앵커 기능과 무관하게 실재하는 버그다:
- `apps/api/src/libs/event/presentation/dto/update-event.dto.ts:87-90` — `parentEventId?: string | null` + `@ValidateIf` + swagger nullable. 런타임은 이미 3상인데(`event.service.ts:866-867, 1006-1017`) 계약이 `{"type":"string"}`이라 타입 안전한 '최상위로 올리기' 호출이 불가능하다.
- `apps/api/src/libs/event/application/event.service.ts:1396-1425` `restoreEvent` — 부모가 소프트삭제면 같은 tx에서 `parentEventId=null` + `extraParentLinks` deleteMany(INV-2 유지) + `restoredAsRoot: true` 고지. 안 A의 형태를 그대로 쓴다(안 B의 가드는 엣지 정리를 빠뜨려 그 자체가 INV-2를 깬다).
- 이후 `npm run build:nestia` → `apps/web-admin/src/shared/api/` 래퍼 갱신.

### 프론트 — 핵심 계약 3개

**① 앵커는 파생이 기본, 오버라이드가 예외다.** 신규 `apps/web-admin/src/features/event-hierarchy/model/anchor.ts`:
- `getDescendantCount(node)` — 로드된 `hierarchy` 서브트리 재귀 카운트
- `isAnchorEvent(node)` = `node.anchorOverride === 'ANCHOR' || (node.anchorOverride !== 'PLAIN' && getDescendantCount(node) >= 1)` → 오늘 20건 전량 포착(오버라이드 0건)
- 임계 3은 쓰지 않는다(보불전쟁 cc=2, 1차 아편전쟁 cc=2, 보오전쟁 cc=1이 탈락하므로)
- **판정은 이 함수 하나로만.** 목록·트리·상세·칩·정렬이 전부 여기를 경유한다(근인 4의 재발 방지 — 지면마다 다른 걸 세던 문제)
- 배치0은 `anchorOverride` 필드 없이 파생만으로 먼저 나가고, 배치1이 이 함수 **한 줄만** 바꿔 오버라이드를 얹는다

**①-b 라벨은 루트 여부로 갈린다** (사용자 결정 2 — 비루트 앵커 허용):
- `isTreeRoot && isAnchorEvent` → '**최상위 사건**' + ⚑
- `!isTreeRoot && isAnchorEvent` → '**하위 N건**' + ⚑ (조망 진입은 되지만 '최상위'라 부르지 않는다)
- 오늘 비루트 앵커는 2건: `프랑스의 대러시아 차관`(자손 4, 조부 `러불 동맹`), `엔비디아 …블랙웰 공개`(자손 1)

**② 루트 술어를 두 이름으로 분리한다** (안 A가 하나로 묶으려다 만든 오염원 회피):
- `isTreeRoot(event)` = `!event.parentEventId` — 서버 `ROOT_EVENT_WHERE`(`domain/event-hierarchy.ts:15`)의 프론트 미러. `useEventFilters.ts:329`, `event-tree-view.tsx:178`, `events.page.tsx:1263·1273` 4곳 치환
- `isRenderRoot(node, scopeIds)` = 부모 id가 현재 모수 안에 없음 — 앵커 모드·유령 부모용. **`depth === 0`으로 최상위를 판정하지 않는다**(필터 중 `matched-rows.ts:35-54`가 depth를 재계산해 자식이 depth 0으로 승격된다)

**③ 앵커 모드는 펼침이 아니라 모수 축소다.** `useEventFilters`에 스코프 인자를 주입해 모수를 앵커의 조상 체인 판정으로 좁힌다. 자동 펼침 래치(`useEventHierarchy.ts:341-358`)와 싸우지 않기 위한 유일한 방법이다.

## 미해결 · 사용자 결정 필요

1. ~~**'최상위 사건 지정'의 의미 확정.**~~ **✅ 종결 (2026-08-11) — (a) 구분·표시 + (b) 모으기 + (c) 빈 사건 선언, 셋 다.** 각각 배치0 / 배치2 / 배치1이 담당한다. (c) 때문에 스키마 1컬럼이 되살아났으나, 안 C 원안이 아니라 백필 없는 3상 오버라이드 형태다.

2. **앵커 임계.** 자손 ≥1(20건, 채택안)인가 ≥3(12건)인가. 판정 렌즈 하나는 3을 권고했고 적대 검증은 3이 보불전쟁·아편전쟁·보오전쟁을 탈락시킨다고 반박했다. 1로 정했으나 사용자가 목록을 보고 "2건짜리는 앵커가 아니다"라고 판단하면 상수 하나로 바꿀 수 있다.

3. ~~**비루트 앵커(하위 앵커) 허용 여부.**~~ **✅ 종결 (2026-08-11) — 허용하되 라벨 분리.** 루트 앵커만 '최상위 사건'이라 부르고, 비루트 앵커는 '하위 N건' 배지로 표기하되 조망 진입은 동일하게 연다. 오늘 대상 2건(`프랑스의 대러시아 차관` 자손 4 / 엔비디아 블랙웰 자손 1). 이 결정으로 배치3의 `isRenderRoot` 주입 spec(K4)이 선택이 아닌 **필수 종료 게이트**가 된다 — 비루트 앵커 진입 시 백지 화면이 나는 경로가 정확히 이것이기 때문이다.

4. **다중 상위(`EventParentLink`) 존치 여부.** 살아있는 엣지 0건인데 쓰기 가드·409 분기·승격 픽커·409 문구가 상시 유지비로 남는다. 존치하면 앵커 조망에서 '주 상위 트리 정본 + EXTRA 1-hop 부록' 규약을 계속 지켜야 한다. (`EventRelation` 2행 드랍 여부는 기존 미결과 동일 성격.)
