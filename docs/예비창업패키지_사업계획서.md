# Papyrus 예비창업패키지 사업계획서

> **Papyrus**: 역사적 사건·인물·관계를 체계적으로 관리·시각화하는 지식 그래프 플랫폼
>
> 본 문서는 Papyrus 프로젝트를 기반으로 한 예비창업패키지 사업계획서이며, **지식 관리 플랫폼(웹)** 과 **RESTful API** 를 중심으로 서비스를 상세히 설명합니다.

_(한 줄 요약)_ 관계 기반 지식 그래프로 역사·시사 맥락의 사건·인물·관계를 관리·시각화하는 구독형 웹 서비스(Papyrus)

## 1. 문제인식

### 1-1. 창업아이템 배경 및 필요성

> **작성 방향**: 예비창업패키지 심사 항목 기준 — ① 창업 동기(창업자 관점의 문제 발견 계기), ② 사회·시장 문제의 심각성·규모, ③ 기존 대안의 한계, ④ 해결책의 방향성과 차별성

---

#### 1-1-1. 창업 동기

**창업자의 직접 경험**

창업자는 평소 역사와 시사에 깊은 관심을 가지고 있었습니다. 특정 사건을 깊이 이해하려 할수록 그 배경에 얽힌 인물·국가·조직의 관계가 복잡하게 연결되어 있다는 것을 느꼈고, 이를 체계적으로 정리하고 싶다는 필요를 꾸준히 가져왔습니다.

이 과정에서 손에 잡히는 도구를 순서대로 모두 활용해 보았지만, 매번 구조적 한계에 부딪혔습니다.

- **iOS 메모 / 삼성 메모** — 즉각적인 기록에는 유용했으나, 사건이 누적될수록 메모가 수백 개로 분산되어 특정 인물이 참전한 전투나 관련 사건을 찾기 위해 전체 메모를 수동으로 탐색해야 했습니다. 인물과 사건 간의 관계를 연결할 수단이 없었습니다.
- **아래아한글 / 워드** — 표와 본문을 조합하여 국가별·인물별로 정리를 시도했으나, 정보가 수십 페이지에 걸쳐 분산되었고 사건·연도·국가가 혼재된 문서는 시간이 지나면 작성자 본인도 파악하기 어려운 상태가 되었습니다.
- **노션** — 가장 유연한 도구였으나, 사건·인물·국가를 연결하는 데이터 구조를 직접 설계하는 데만 수십 시간이 소요되었습니다. 데이터가 증가할수록 관계 관리가 어려워졌고, 타임라인 및 관계 그래프 구현은 불가능했습니다.
- **나무위키·위키피디아** — 정보 탐색 시 관련 문서가 수십 개로 파편화되어 전체 맥락을 파악하기 위해 다수의 탭을 동시에 열어야 했으며, 탐색한 정보를 자신의 데이터 자산으로 축적할 수 없었습니다.

여러 도구를 거친 끝에 도달한 결론은 명확했습니다. **사건·인물·국가 간의 복잡한 관계를 구조적으로 입력하고, 타임라인과 관계 그래프로 시각화할 수 있는 전용 도구가 존재하지 않는다는 것이었습니다.**

**사용자 검증 — 동일한 문제를 겪고 있는 시장**

이 불편이 개인적인 경험에 그치는지 확인하기 위해, 역사·시사 콘텐츠를 다루는 실무자 및 전공자·관심층과 직접 이야기를 나눴습니다. 직군과 작업 방식은 달랐지만, 핵심 문제는 동일했습니다.

| 대상                          | 현재 사용 도구     | 공통 불편 사항                                                      |
| ----------------------------- | ------------------ | ------------------------------------------------------------------- |
| 역사·시사 유튜브 채널 운영자  | 메모 앱·노션       | 사건-인물-국가 연결 구조 설계 자체가 어려워 결국 텍스트 나열로 회귀 |
| 대학교 역사학과 강사          | 엑셀·워드프로세서  | 역대 수반·행정 구조·사건을 매번 각각 따로 조사해 수동으로 조합      |
| 역사 다큐멘터리 제작사 기획자 | 피그마·PPT         | 인물 관계도를 직접 제작, 정보 변경 시 전체 재수정 필요              |
| 역사·정치외교학 전공자        | 학술 DB·위키피디아 | 읽기 전용 구조로 자체 데이터를 입력·관리할 수 없음                  |
| 역사·밀리터리 관심층(개인)    | 위키·메모 앱       | 비구조화 메모 한계 — 관계와 맥락이 사라지고 정보가 파편으로 남음    |

이는 특정 개인의 불편이 아니라, **역사·시사 데이터를 직접 정리하고 구조화하려는 누구에게나 공통으로 나타나는 구조적 공백**임을 확인했습니다.

**창업의 확신 — 기술적으로 해결 가능하고, 지금이 적기다**

이 문제는 기술적으로 충분히 해결 가능합니다. 관계형 데이터베이스, 지식 그래프, 시계열 시각화는 이미 성숙한 기술입니다. 다만 이를 역사·시사 도메인에 특화하여 비개발자도 활용할 수 있는 형태로 구현한 제품이 시장에 존재하지 않았을 뿐입니다.

시장 환경 또한 지금이 적기입니다. 교육부의 디지털 교과서 전면 도입(2025~), 문화유산 디지털화 정책 확대, AI 서비스의 구조화 데이터 수요 증가로 역사·시사 도메인 지식 그래프의 필요성이 그 어느 때보다 높아지고 있습니다.

창업자가 직접 체감한 문제, 시장 실무자들의 검증, 그리고 해결 역량과 시장 환경의 정합성 — 이 세 가지가 Papyrus 창업의 출발점입니다.

#### 1-1-2. 사회·시장적 문제 — 규모와 심각성

**(1) 역사·교육 콘텐츠 시장의 급성장과 데이터 인프라 부재**

- 국내 에듀테크 시장 규모는 2022년 기준 약 **7조 원** 수준으로 연평균 15% 이상 성장 중이며(교육부·KERIS), 역사·사회 교과 디지털 자료 수요가 꾸준히 증가하고 있습니다.
- 유튜브 역사·교양 채널 상위 10개의 구독자 합산은 **500만 명 이상**(2024년 기준)으로, 역사 콘텐츠 소비는 이미 대중화되어 있습니다.
- 그러나 이를 **제작하는 측(연구자·교사·크리에이터)** 이 활용할 수 있는 전문 데이터 관리 플랫폼은 국내에 전무하며, 여전히 위키·포털·엑셀·노션의 조합에 의존하고 있습니다.

**(2) 역사 드라마·미디어 흥행이 증명하는 역사 콘텐츠 수요**

- 〈고려거란전쟁〉(2023~2024), 〈세작, 매혹된 자들〉(2024), 〈정년이〉(2024) 등 역사 드라마의 연이은 흥행은 대중의 역사 인물·사건에 대한 관심이 단순한 교육 수요를 넘어 **엔터테인먼트·문화 소비** 영역으로 확장되고 있음을 보여줍니다.
- 드라마 방영 직후 포털 검색량이 급증하는 패턴은 **역사 정보에 대한 즉각적·대중적 수요**가 실재함을 시사합니다. 그러나 이 수요를 충족할 수 있는 플랫폼은 파편화된 위키·포털 검색에 그치며, **콘텐츠 제작사·방송사·OTT** 가 필요로 하는 구조화된 역사 데이터 인프라는 존재하지 않습니다.
- Papyrus는 이 흥행 사이클에서 발생하는 **"콘텐츠 제작 → 대중 관심 → 추가 제작"** 의 수요 고리에 데이터 인프라로 연결될 수 있습니다.

**(3) 디지털 전환 정책의 가속화와 데이터 연계 공백**

- 교육부·KERIS의 **디지털 교과서 전면 도입(2025~)** 정책에 따라, 역사 교과의 디지털 자료 체계화 수요가 급증하고 있습니다.
- 국사편찬위원회, 한국학중앙연구원 등 공공 기관들은 디지털 아카이브를 개별적으로 구축하고 있으나, **기관 간 데이터 연계·통합 체계가 부재**하여 동일한 인물·사건 데이터를 기관마다 따로 입력·관리하는 비효율이 발생하고 있습니다.
- 문화체육관광부의 **'디지털 문화유산 전략(2023~2027)'** 에서도 "플랫폼 간 데이터 연계 부재"를 핵심 과제로 명시하고 있습니다.

**(4) AI 시대의 지식 그래프 수요 — 구조화 데이터의 전략적 가치**

- ChatGPT·Perplexity 등 AI 서비스는 **구조화된 지식 그래프(Knowledge Graph)** 를 학습 데이터로 활용합니다. 그러나 역사 도메인의 한국어 구조화 데이터는 극히 부족합니다.
- Google Knowledge Graph, Wikidata 등 글로벌 지식 그래프 시장은 2023년 약 **9억 달러** 규모로 연평균 20% 이상 성장 중입니다(Grand View Research).
- 역사 분야 관계 데이터(인물–사건–국가–조직)가 체계화되면 AI 학습·검색 강화·추천 시스템의 핵심 자원이 되며, 이는 단순 교육 플랫폼을 넘어 **데이터 인프라 사업**으로의 확장 가능성을 열어줍니다.

#### 1-1-3. 기존 서비스의 구조적 한계

역사·지식 정보를 다루는 기존 서비스들은 다음과 같은 구조적 한계를 가집니다.

**① 나무위키·위키피디아 — "정보는 많지만, 연결이 없다"**

| 한계                  | 구체적 현상                                                                                                          |
| --------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 정보 파편화           | "트럼프 관세 정책", "미중 무역전쟁", "중국 WTO 가입" 등이 개별 문서로 분산 → 관계 파악을 위해 수십 개 탭을 열어야 함 |
| 비구조화된 자유 형식  | 문서마다 작성 방식이 달라 일관성 없음 → 데이터 추출·분석 불가, 관계 정보가 텍스트 속에 묻힘                          |
| 시간적 맥락 부재      | 사건들의 시간순 연결이 어려움 → 인과관계 추적 불가, 통합 타임라인 없음                                               |
| 검색 기반 탐색만 가능 | "이 사건과 관련된 다른 사건은?" — 수동으로 클릭을 반복해야 하며, 자동 추천·관계 탐색 불가                            |

**② 뉴스·미디어·포털 — "최신 정보만 있고, 배경이 없다"**

| 한계             | 구체적 현상                                                    |
| ---------------- | -------------------------------------------------------------- |
| 최신 정보만 제공 | 역사적 배경·인과관계 부재 → "왜 이렇게 되었나?"에 대한 답 없음 |
| 단편적 보도      | 개별 사건만 다룸, 복합적 관계 설명 구조 없음                   |

**③ 학술 데이터베이스(RISS, DBpia 등) — "전문가만 쓸 수 있다"**

| 한계        | 구체적 현상                                            |
| ----------- | ------------------------------------------------------ |
| 전문가 전용 | 일반 연구자·크리에이터 접근 어려움, 고비용 구독 구조   |
| 검색 중심   | 탐색·시각화 기능 없음, 관계 기반 네비게이션 불가       |
| 읽기만 가능 | 사용자가 데이터에 기여·편집할 수 없는 단방향 소비 구조 |

**④ 노션(Notion) 등 범용 도구 — "유연하지만 역사엔 맞지 않다"**

| 한계               | 구체적 현상                                                                        |
| ------------------ | ---------------------------------------------------------------------------------- |
| 역사 도메인 비특화 | 사건·인물·국가 전용 스키마 없음 → 구조 설계에만 수십 시간 소요, 결과물 재활용 불가 |
| 제한적 시각화      | 테이블·보드 뷰만 지원 → 관계 네트워크 그래프·통합 타임라인·교전국 관계도 구현 불가 |
| 수동적 관계 연결   | 모든 관계를 일일이 수동 설정 → 자동 연결 없음, 데이터 증가 시 관리 불가능          |
| 대규모 확장 부적합 | 개인/소규모 팀 최적화 → 기관 단위 데이터 표준화·공유·API 연동에 구조적 한계        |

> **핵심 포지셔닝**: "노션으로 역사 DB 만들기 = 엑셀로 ERP 시스템 만들기" — 가능은 하지만, 운영 중 무너지는 구조입니다. 기업이 회계·인사·재고를 엑셀로 관리하다 ERP로 전환하듯, **역사·지식 도메인 데이터를 전문적으로 구축·관리하는 ERP, 즉 '지식 도메인 ERP'가 아직 존재하지 않습니다.** Papyrus는 이 공백을 채우는 최초의 전문 솔루션입니다.

**기존 서비스 한계 종합 요약**

| 한계 영역                    | 현상                                                                                     | 영향                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------ |
| 정보 파편화                  | 관련 정보가 수십~수백 개 문서에 분산                                                     | 탐색에 과도한 시간 소요              |
| 비구조화 데이터              | 자유 형식으로 체계적 분석·추출·API 활용 불가                                             | 데이터 재사용성 제로                 |
| 관계 파악 어려움             | 사건-인물-국가-조직 간 관계를 직관적으로 파악 불가                                       | 맥락 이해 실패, 콘텐츠 품질 저하     |
| 시간적 흐름 단절             | 역사 사건의 원인·결과를 시계열로 추적 불가                                               | 인과관계 분석 불가능                 |
| 시각화 부재                  | 텍스트 중심 서비스, 관계 그래프·타임라인 없음                                            | 교육·콘텐츠 제작 활용 한계           |
| 수동적 소비 구조             | 기여·창조 불가, 읽기만 가능한 플랫폼                                                     | 사용자 생산성 및 참여도 저하         |
| **역대수반 정보 단절**       | 역대 대통령·국왕·수상 목록이 인물·사건·국가 정보와 분리되어 관리                         | 통치 기간·정책·사건 연계 분석 불가   |
| **행정 정보 비연결**         | 행정부처·행정구역이 독립 문서로 존재 → 어느 시대 어느 지역 맥락인지 파악 어려움          | 역사·현재 행정 구조 비교 불가        |
| **국가·왕조 계보 관리 불가** | 현대 국가와 역사적 국가(왕조·제국·속국 등)의 계보·연결 관계를 한 곳에서 관리할 수단 없음 | 국가 변천사·건국·멸망 맥락 추적 불가 |
| **조직 정보 고립**           | 군사조직·국제기구·정치단체 등의 구성·역할·참여국이 사건·인물과 분리되어 파편화           | 전쟁·외교·조약의 주체 파악 어려움    |

#### 1-1-4. 근본 문제: "역사·지식 도메인 전용 ERP가 존재하지 않는다"

기업은 회계·인사·재고 관리를 위해 ERP(전사적 자원 관리 시스템)를 도입합니다. ERP 이전에는 엑셀과 개별 문서로 관리했지만, 데이터가 쌓이고 부서 간 협업이 필요해지면서 전용 솔루션이 필수가 되었습니다.

**역사·지식 데이터도 정확히 같은 상황입니다.** 교육기관·연구소·콘텐츠 제작사는 지금도 노션·엑셀·한글 문서로 역사 데이터를 정리하고 있습니다. 그러나 데이터가 쌓일수록 관계 연결은 끊어지고, 시각화는 불가능해지며, 재사용은 요원해집니다.

문제는 단순합니다. **역사·지식 도메인 전용 ERP — 즉, 사건·인물·국가·왕조·행정·조직을 통합 관리하고 자동으로 연결·시각화해주는 전문 플랫폼이 시장에 존재하지 않습니다.**

- **나무위키**: 불특정 다수가 자유 형식으로 편집 → 기관이 원하는 데이터 표준화·품질 관리 불가, 자체 데이터 자산으로 활용 불가
- **노션·엑셀**: 유연하지만 역사 도메인 스키마가 없어 초기 설계에 수십 시간 소요, 관계 시각화 불가, 데이터 규모가 커질수록 관리 붕괴
- **학술 DB**: 읽기 전용 구조, 기관이 자체 데이터를 입력·관리할 수 없음
- **AI(ChatGPT)**: 생성된 답변이 휘발되며 기관 데이터 자산으로 축적 불가, 구조화 불가

결론적으로, **역사 도메인 특화 스키마 + 자동 관계 연결 + 즉각적 시각화 + 기관·개인 단위 데이터 관리**가 가능한 전문 플랫폼 — **지식 도메인 ERP** — 은 현재 시장에 존재하지 않습니다.

#### 1-1-5. Papyrus의 해결 방향 — 구조화·자동화·시각화

Papyrus는 위 한계를 세 가지 핵심 접근으로 극복합니다.

> **핵심 전제**: Papyrus는 교육기관·연구소·콘텐츠 제작사 등 **기관**뿐 아니라, 역사 매니아·밀리터리·시사 등 **깊이 있는 관심을 가진 개인 사용자**까지 **직접 역사·지식 데이터를 입력·구조화**할 수 있는 전문 도구입니다. 기존 도구(노션·엑셀·위키)로 수동 정리하던 작업을 **구조화된 입력 체계 + 자동 관계 연결 + 즉각적 시각화**로 대체합니다.

| 문제 영역                    | Papyrus 해결 방안                                                                                                                                         |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **정보 파편화**              | 통합 입력 체계 — 사건·인물·국가·조직을 단일 시스템에 입력·연결, 분산된 문서·파일 없이 한 곳에서 관리                                                      |
| **비구조화**                 | 도메인 특화 스키마 — 역사 전용 필드(시작일·종료일·장소·교전국·역할 등)로 일관된 구조 보장, 입력 즉시 API·분석 연동 가능                                   |
| **수동 관계**                | 자동 관계 연결 — 사건 입력 시 관련 인물·국가 선택만으로 양방향 관계 자동 생성(사건↔인물↔국가↔조직), 수동 링크 작업 불필요                                 |
| **시각화 부재**              | 입력 즉시 시각화 — 데이터 입력과 동시에 관계 네트워크·타임라인·교전국 관계도·통계 대시보드 자동 생성                                                      |
| **시간 맥락 부재**           | 시계열 자동 구성 — 사건 등록 시 날짜 기반 타임라인 자동 배치, 상·하위 사건 관계 설정으로 인과관계 구조화                                                  |
| **단방향 소비**              | 능동적 구축 경험 — 입력할수록 지식 네트워크가 확장되는 플랫폼, 구축한 데이터가 영구 자산으로 재사용 가능                                                  |
| **역대수반 정보 단절**       | 역대수반 전용 입력 모델 — 국가별 역대 수반 등록 시 재임 기간 기반으로 동일 기간 사건 자동 연결, 수동 메모 없이 통치 맥락 즉시 구성                        |
| **행정 정보 비연결**         | 행정부처·행정구역 구조화 입력 — 국가·시대 선택으로 행정 구조를 계층화 입력, 관련 사건·인물과 자동 연결되어 변천사 타임라인 자동 구성                      |
| **국가·왕조 계보 관리 불가** | 국가·왕조 전용 도메인 — 건국·멸망 시점, 수도·영토 변천, 전신·후신 왕조 계보를 구조화 입력, 동일 시대 타국과의 관계(동맹·교전·속국)를 자동으로 교차 연결   |
| **조직 정보 고립**           | 조직 구조화 입력 — 군사조직·국제기구·정치단체의 창설·해산 시점, 구성국·역할을 입력하면 관련 사건·인물·국가와 자동 연결, 조직 중심 관계 네트워크 즉시 생성 |

#### 1-1-6. Papyrus가 제공하는 새로운 작업 방식: 구축할수록 강해지는 데이터 자산

Papyrus는 **입력할수록 데이터 자산이 자동으로 확장되는 구조**를 제공합니다. 기존 도구와 달리 한 번 입력한 데이터가 연결된 모든 도메인에 자동 반영되어, 구축 비용 대비 활용 가치가 기하급수적으로 높아집니다.

| 가치              | 기존 도구(노션·엑셀)                         | Papyrus                                                                 |
| ----------------- | -------------------------------------------- | ----------------------------------------------------------------------- |
| **데이터 입력**   | 각 문서·셀에 개별 입력, 관계 수동 연결       | 역사 전용 폼으로 입력 → 관련 도메인에 자동 반영                         |
| **관계 관리**     | 링크·참조 수동 설정, 변경 시 전체 재작업     | 사건-인물-국가 관계 자동 생성·양방향 유지                               |
| **시각화**        | 별도 툴 필요, 데이터 변경 시 수동 재제작     | 입력 즉시 타임라인·관계 그래프·대시보드 자동 생성                       |
| **데이터 재사용** | 파일 형태로 분산, 재활용 어려움              | API로 외부 시스템 연동 가능, 동일 데이터를 교과서·강의·연구에 반복 활용 |
| **유지보수**      | 한 곳 수정 시 연결된 모든 문서 수동 업데이트 | 한 곳 수정 시 연결된 전체 데이터 자동 반영                              |

#### 1-1-7. 구체적 문제 사례 — Before & After

> **전제**: Papyrus는 교육기관·연구소·콘텐츠 제작사와 역사 매니아·개인 연구자 등 **모든 이용자**가 **직접 데이터를 입력·구조화하는 플랫폼**입니다. 아래 사례는 "기존 도구로 데이터를 정리할 때의 불편함"과 "Papyrus로 입력·관리할 때의 효율 차이"를 비교합니다.

**사례 1: "미중 무역전쟁 교육 자료를 만들려면?"**

| 방식          | 과정                                                                                                                                                  | 결과                                                          |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| **기존 방식** | 위키·포털 탐색 → 관련 사건·인물 각각 메모 → 노션에 수동 정리 → 관계 직접 연결, **반나절~하루**                                                        | 정리 후에도 관계 시각화 불가, 업데이트 시 전체 재작업         |
| **Papyrus**   | "미중 무역전쟁" 사건 입력 시 → 관련 인물·국가 선택으로 관계 자동 연결 → 선행 사건(WTO 가입 등) 연결 시 타임라인 자동 생성, **1~2시간 내 구조화 완료** | 입력 즉시 관계 그래프·타임라인 시각화, 추가 입력 시 자동 확장 |

**사례 2: "이순신 인물 데이터베이스를 구축하려면?"**

| 방식          | 과정                                                                                                                                 | 결과                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| **기존 방식** | 참여 전투·소속 조직·관련 인물 각각 별도 문서로 작성 → 노션·엑셀에서 수동 링크 → 타임라인 별도 제작, **수십 시간**                    | 정보가 여러 파일에 분산, 관계 시각화 없음                               |
| **Papyrus**   | 이순신 인물 등록 → 참여 사건 연결 시 전투 목록·타임라인 자동 구성 → 소속 조직·동시대 인물 선택으로 관계도 자동 생성, **효율적 입력** | 단일 페이지에 전투·관계·타임라인 통합, 추후 관련 사건 입력 시 자동 반영 |

**사례 3: "임진왜란 데이터베이스를 구축한다면?"**

```
기존 방식 (노션/엑셀):
- "임진왜란" 문서 작성 → 하위 전투 각각 별도 페이지 생성 → 수동 링크
- 이순신·선조 인물 페이지 별도 작성 → 임진왜란과 수동 연결
- 조선-일본 관계 별도 정리 → 타임라인 별도 제작
→ 파일 수십 개, 관계 수동 관리, 한 곳 수정 시 전체 업데이트 필요

Papyrus 방식:
1. "임진왜란" 사건 등록 (시작일·종료일·장소·카테고리)
2. 하위 사건(한산도 대첩, 명량 해전 등) 등록 → 상위 사건 선택만으로 타임라인 자동 배치
3. 관련 인물(이순신, 선조 등) 선택 → 이순신 인물 페이지에 전투 목록 자동 반영
4. 교전국(조선 vs 일본) 설정 → 교전국 관계 그래프 자동 생성
→ 추가 입력할수록 지식 네트워크가 자동으로 확장됨
```

- **생산성·재사용**: 기관·개인 모두 수동 문서 작업을 구조화 입력으로 대체 — 한 번 구축한 데이터를 강의·콘텐츠·개인 학습에 반복 활용

### 1-2. 창업아이템 목표시장 현황 분석

#### 1-2-1. 목표시장 정의

| 구분         | 정의                                                                                                    | Papyrus 포지션                             |
| ------------ | ------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **1차 시장** | 역사·밀리터리·시사 등 **관심 분야를 데이터로 쌓고 싶은 개인**(심화 학습·자기주도 연구·체계적 정리 욕구) | 무료→유료 전환, **월 구독**                |

**근본적 차이: "지식 도메인 ERP"의 부재**

기업이 회계·인사·재고를 엑셀로 관리하다가 SAP·오라클 같은 ERP로 전환했듯, 역사·지식 도메인 데이터도 동일한 전환점에 와 있습니다. 그러나 **역사·지식 도메인 전용 ERP는 아직 존재하지 않습니다.** Papyrus는 이 공백을 최초로 채우는 플랫폼입니다.

| 측면              | 나무위키/위키피디아 | 노션·범용 도구     | **Papyrus (지식 도메인 ERP)**                        |
| ----------------- | ------------------- | ------------------ | ---------------------------------------------------- |
| **포지셔닝**      | 백과사전 (조회용)   | 범용 문서 도구     | **역사·지식 데이터 전용 ERP**                        |
| **입력 구조**     | 자유 텍스트         | 범용 템플릿        | **역사 도메인 전용 스키마**                          |
| **데이터 형식**   | 비구조화            | 반구조화           | **완전 구조화 (국가·왕조·인물·사건·조직·행정 통합)** |
| **관계 관리**     | 하이퍼링크(수동)    | 수동 링크          | **자동 양방향 관계 (입력 시 자동 연결)**             |
| **시각화**        | 없음/제한적         | 테이블·보드만 가능 | **타임라인·관계 그래프·대시보드 자동화**             |
| **데이터 소유권** | 플랫폼 소유         | 자체 관리 가능     | **기관 자체 데이터 자산화**                          |
| **API 연동**      | 제한적              | 불가(기본)         | **완전한 RESTful API**                               |
| **확장성**        | 무제한(관리 어려움) | 소규모 최적화      | **기관 단위 대규모 지원**                            |

#### 1-2-4. 시장 기회 요약

- **FSD(Feature-Sliced Design, 기능 단위 설계 방법론)** 적용: 화면·기능·데이터 계층을 명확히 분리하여 유지보수·확장 용이

- **쿠키 기반 인증**: access_token, refresh_token, 세션 유지
- **Lazy Loading**: 페이지별 코드 스플리팅, 로더 기반 데이터 사전 로딩

### 2-2. 창업아이템 개발 계획

#### 2-2-0. 제품 구조와 솔루션(실현 가능성) 정합

| 구분                  | 내용                                                                                                                                                                               |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **현재 제품 형태**    | **웹 애플리케이션 1종**(지식 관리 플랫폼) + **REST API** + DB. 역사 도메인 데이터의 등록·조회·시각화가 동작하는 MVP를 보유한다.                                                    |
| **분리하지 않는 것**  | 소비자 전용 **별도 웹 클라이언트는 두지 않는다.** 개인 이용자·기관 이용자 모두 **동일 플랫폼·동일 API**를 전제로 하며, 차이는 **계정·조직(팀)·권한·요금제**로 단계적으로 반영한다. |
| **사업계획과의 연계** | **구독·결제**와 **워크스페이스·초대**(§2-2-2 6~7차)로 구현한다. 협약 8개월 내에는 **과금 연동·Free/Pro 플랜·최소 팀 확장**을 우선 완료하는 것을 목표로 한다(§2-3·로드맵과 연동).   |

#### 2-2-1. 개발 성과(현재까지) 및 기능 범위

아래는 **사업계획서상 실현가능성 근거**로, **① 서버·데이터(API·DB)**와 **② 지식 관리 웹(화면)** 관점에서 **현재 제품에 반영된 범위**를 정리한 것이다. (화면·경로 상세는 §2-1-2, 부록 A 참고.)

**범위 표기** — **핵심 역사 도메인(사건·인물·국가·관계 시각화 등)**은 **서비스 수준에서 동작이 확인된 범위**로 기술한다. **고급 검색·다중 역할 권한·일괄 업로드·유료 구독·팀 협업** 등은 **§2-2-2 협약기간 추진 과제**로 구분한다. **국가 거시통계·무역·기업**은 **데이터 구조·일부 API가 준비**되어 있으나, **화면·실데이터 연동은 단계적으로 완성**하는 영역으로, 아래 표에서 **데이터·모델**과 **화면·연동**을 나누어 기술한다.

#### 2-2-3. 기술·품질 구체화 방안

1. **품질·일관성**
   - **저장 항목·입력 규칙**에 따른 검증, 입력 단계에서의 안내·오류 처리 강화

   - 단일 코드베이스 기반 도메인 모듈 구조 유지, 필요 시 API 버전 관리·캐시·CDN 도입으로 대용량·다사용자 대비

3. **보안·규정**
   - 인증 토큰·권한 모델을 통한 접근 통제(계정·소유 기반에서 **역할·팀 기반으로 단계 고도화**, §2-2-2 **3차**), 개인정보·민감 정보 보호
   - 백업·재해복구 절차 정비

#### 2-2-4. 기능·성능 차별성 및 경쟁력 확보 전략

##### (1) 핵심 기능 차별성 — 경쟁 서비스가 제공하지 못하는 것

Papyrus의 차별성은 단순한 기능 추가가 아니라, **기존 어떤 도구도 하나의 시스템으로 통합하지 못한 도메인 구조**를 최초로 구현한 데 있습니다.

| 차별화 영역                     | 경쟁 서비스(노션·위키·학술DB)        | Papyrus                                                                         |
| ------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------- |
| **도메인 통합 모델**            | 사건·인물·국가·왕조·행정을 각각 분리 | 단일 시스템에서 전 도메인을 상호 연결 — 입력 즉시 전체 관계망 자동 구성         |
| **국가·왕조 전용 구조**         | 지원 없음                            | 건국·멸망·수도·영토·계보·속국 관계 전용 스키마, 현대 국가와 역사 국가 동시 관리 |

##### (2) 시각·인포그래픽 역량 — 데이터를 “한눈에 읽히는 지식”으로

범용 문서·표 도구와 달리, Papyrus는 **구조화된 역사·지식 데이터를 시각 자산으로 바로 쓰일 수 있게** 만드는 데 강점이 있습니다. 별도 디자인 전문 툴 없이도 **대시보드·연대표·지도·관계 그래프**로 맥락을 전달합니다.

**국가·거시** — 국가 상세 **대시보드**에 경제·인구·수출·수입 등을 **차트·카드형 지표**로 묶습니다. 지표 간 비교가 되도록 하였고, 교육·콘텐츠·브리핑에 **화면 그대로 쓸 수 있는 밀도**를 지향합니다.

**시간** — 국가 맥락 **사건 연대표**, 행정·각료 **시간축**, 사건 **상·하위·계층** 요약을 둡니다. 통치·외교·전쟁의 **순서와 병렬 맥락**을 한 화면에서 읽게 합니다.

**공간** — 행정구역·자연·인프라를 **지도와 목록**으로 함께 둡니다. 국가·지역 데이터와 연결하고, 지리와 역사를 **동시에** 다루는 수업·연구·기획에 맞춥니다.

**관계·네트워크** — 군사·외교 사건의 교전국·세력 관계를 **관계 그래프**로 풉니다. 관계 유형·강도·진영을 구분하고, 동맹·적대를 **다이어그램 수준**으로 설명할 수 있게 합니다.

**사건 요약** — 영향 지표, 지휘·병참 요약, 계층 구조를 한곳에 모읍니다. 기사·강의·영상 대본에 필요한 **핵심 수치와 구조**를 빠르게 가져가게 합니다.

**통계** — 인구·경제는 **시계열·막대·면적 차트**, 인구 구조는 **피라미드형**으로 표현할 수 있게 설계하였습니다. 실데이터와 화면의 완전한 연동은 **협약기간 개발 계획**에서 보강합니다.

이 경험은 **역사·지식에 맞게 사건·인물·국가를 한데 묶어 둔 구조**와 **인포그래픽·시각화가 한 제품에 묶여** 있기에 가능합니다. 표·문서 위주 도구와 달리 **교육·콘텐츠·연구 산출물의 설득력·완성도**에서 차별화됩니다.

##### (3) 경쟁력 확보 전략 — 단기·중기·장기

**단기 (0~6개월): 입력·연결 설계와 시각 품질로 차별화**

- **사건·인물·국가를 잇는 입력 항목·관계 설계**를 촘촘히 한다. **대시보드·연대표·관계 그래프** 등 **화면·그래프 품질**을 함께 끌어올린다. 파일럿·데모에서 **한눈에 전달되는 사례**를 확보한다.
- 교육기관·연구소 1~2곳과 파일럿 계약 → **실제 데이터가 쌓인 사례** 확보
- 파일럿 피드백으로 **입력 규칙·화면**을 고도화한다. **따라 만들기 어려운 ‘역사 지식 인포그래픽’ 경험**으로 포지셔닝한다.

**중기 (6~12개월): 구독 매출 성장**

- 입력·축적된 데이터는 **이용자 자산**이다. 쌓일수록 이탈 비용이 커진다. 외부에 데이터를 팔지 않는다.
- **유료 전환**: Pro, **대학·학회·세미나·전문 매체·크리에이터 협업** 및 **타깃 메일·제안**으로 **개인·준전문가·팀** 유료층 확대
- **팀·파일럿**: 워크스페이스·좌석 확대

**장기 (1년 이후): 브랜드·글로벌·제품 깊이**

- 국내 **역사·지식 분야 심화 학습**용 구조화 도구로 인지도를 확보한다. 개인·팀이 **같은 엔진·같은 과금**으로 성장한다.
- 한국사 중심에서 세계사·다국어·해외 사용자로 확장
- 검색·품질·협업을 고도화한다(선택적 AI 보조 등). **구독 가치**를 지속 강화한다. 데이터 **판매**가 아닌 **구독** 중심 모델을 유지한다.

### 3-1. 창업아이템 비즈니스 모델

#### 3-1-1. 수익원 구조

**매출의 중심은 한 가지다.** 이용자가 제품을 쓰는 대가로 내는 **서비스 이용료(월·연 구독)**. 무료 체험(**Free**)으로 가치를 확인한 뒤 유료(**Pro**)로 전환하는 **B2C·소규모 B2B(팀)** 모델을 본다. 팀·워크스페이스는 **별도 매출원을 늘리기보다**, Pro 안에서 **좌석·저장·권한**을 확장하는 **동일 구독·플랜 확장**으로 취급한다.

| 구분 | 내용 | 성격 |
| --- | --- | --- |
| **① 핵심 수익** | **개인·팀 Pro** — 월·연 구독(결제 주기·연간 할인 등은 출시 시 정책으로 정함) | **직접 매출** |
| **② 동일 수익원 내 확장** | Pro 범위에서 **좌석 추가·워크스페이스·용량** — 팀·연구실 등 소규모 조직 단위 과금 | ①의 **확장 과금**(별도 사업부·별도 상품군이 아님) |
| **③ 전략적 비매출(보조)** | 정부 지원·공공 과제·업무협약·파일럿 지원금 | **매출 항목이 아님** — **자금·검증·레퍼런스** |
| **④ 채택하지 않는 모델** | 구조화 데이터·API·연동 인터페이스의 **제3자 판매·라이선스·데이터 중개** | 수익원에서 **제외**(정책) |

**제품 가치의 축** — **열람·탐색**(그래프·연대표·대시보드로 **볼 수 있음**)과 **직접 작성·적립**(사건·인물·관계를 **본인이 입력·축적**)이 한 제품 안에서 이어진다. **완성형 백과나 타인이 채운 DB를 파는 구조가 아니라**, **모든 표본·관계는 이용자(개인·계정)가 쌓아 올린 결과**를 전제로 한다 — 그래서 **데이터 자체를 상품화해 파는 수익**은 두지 않고, **접속·기능·협업 가치에 대한 구독**으로만 환산한다.

**요약** — 수익원 = **구독**(개인·팀 확장 포함). **③**은 현금 유입이 있어도 **사업 매출 구조의 주축이 아니라** 검증·신뢰 확보용으로 구분한다. 가격·플랜 예시는 **§3-1-3**, 수익 성장 타임라인은 **§3-3-1**과 맞춘다.

#### 3-2-2. Go-to-Market 실행 계획

**(1) 1단계: 검증(0~4개월)**

- **목표**: 베타·파일럿 전반에서 **시장 적합성** 신호(재방문·유료 의향) 확보
- **액션**:
  - **개인**: **관련 학과 교수·대학원·연구실**, 시사·국방·역사 **언론·크리에이터·유튜브** 등에 **소개 메일·제안서·무료 데모**, 강의·세미나·학회 부스로 **초기 사용자 확보**, 인터뷰·Free→Pro 전환 실험
  - **기관**: 교육·역사 콘텐츠 1~2곳 무상/저가 파일럿, 실데이터 피드백
  - 파일럿·베타 사례를 사례 스토리로 문서화

**(2) 2단계: 초기 상용화(4~8개월)**

- **목표**: 유료 전환, **월 구독 매출** 목표 설정(개인·팀 Pro)
- **액션**:
  - Pro 출시(저가·명확한 혜택), 온보딩·리텐션 메시지 정비
  - 파일럿 → Pro(팀 좌석 확장) 전환, 교육 박람회·학회·데모데이 참가
  - 교육·연구·제작 팀 대상 1:1 직접 제안(제안서·데모)

**(3) 3단계: 확장(8~12개월~)**

- **목표**: 유료 사용자 수·**월 구독 매출** 가속, 팀·워크스페이스 확대, **선택적** 공공·업무협약(검증·레퍼런스)
- **액션**:
  - **전문가·크리에이터·교육기관 대상 아웃바운드**(메일·세미나·사례집)로 **개인·준전문가 유입** 극대화(데이터/API **판매 없음**)
  - 국사편찬위원회·한국학중앙연구원 등 업무협약·과제 신청
  - 초기창업패키지·창업도약패키지 등 후속 지원사업 검토

#### 3-2-3. 성장·유입 (채널·실행)

초기에는 인력 대비 효과가 큰 경로에 비중을 둔다. **교수·연구실 등 전문가·교육기관 아웃바운드**(메일·방문·세미나·강의 데모)와 **교육기관·연구소·제작사 직접 영업**(제안서·파일럿·데모)에 각각 전체의 약 3할 전후를 배분하고, **시사·역사·군사 크리에이터·기자** 맞춤 제안·샘플 계정에 약 2할, **학회·교육 박람회·데모데이** 등 오프라인 행사에 약 1할, **공식 사이트·블로그** 인바운드에 약 1할 수준을 가정한다. 비중은 실적에 따라 조정한다.

- **누구**: 역사·시사·군사 **크리에이터·미디어**, **교수·연구실**, 교육·콘텐츠 **제작·기관** 담당.
- **어디서**: 한국사·정치외교·군사학 등 **학회**·학술대회, 교육 박람회·에듀테크 행사, 대학 세미나·워크숍.
- **어떻게**: 맞춤 **메일·1p 제안·데모·샘플·체험 계정**, 오프라인 **네트워킹**, 파일럿·**사례** 확보.
- **협약 8개월(예시)**: 전반 **제안 누적**, 학회·박람회 **1~2회** 참가, 파일럿 **1곳**, 후반 **사례·온보딩·전환** 메시지 정비. 건수·일정은 학회 캘린더에 맞추어 조정.
- **KPI**: 발송·응답·데모·미팅, 행사 리드, (과금 출시 후) **무료→유료 전환**·활성 사용자.

#### 3-2-4. 경쟁력 유지 전략

- **데이터 축적**: 고품질 구조화 데이터가 진입 장벽, 네트워크 효과

#### 3-2-5. 경쟁제품·경쟁사 분석 및 시장 진입 전략

**경쟁제품·경쟁사 심층 분석**

대안은 (1) **조회형 백과·포털**, (2) **범용 문서·DB·스프레드시트**, (3) **읽기 중심 학술·저널 인프라**, (4) **공공·기관 전용 DB**, (5) **즉답형 AI**, (6) **범용 그래프·DB 도구**로 나뉜다. 이들은 각각 정보 소비·일반 업무·논문 검색·공식 아카이브·질의 응답·개발자 중심 시각화에 강점이 있으나, **역사 도메인 스키마(사건·인물·국가·왕조·행정·조직)를 한 제품 안에서 입력·소유·시각화**하는 용도로는 부족하거나 비용·역량 문턱이 높다.

### 3-3. 비즈니스 모델·투자유치 전략

#### 3-3-1. 비즈니스 모델(수익화 모델) 요약

Papyrus는 **월·연 구독**으로 수익을 낸다. **열람·탐색**과 **직접 입력·축적**이 한 제품 안에서 이어지고, **데이터는 이용자가 쌓는 구조**다. 팀·워크스페이스는 **좌석·권한**을 확장하는 형태로 둔다. 정부 지원·공공 과제·업무협약은 **자금·검증·레퍼런스**에 활용할 수 있다. **구조화 데이터·연동 인터페이스를 제3자에게 판매하는 수익은 두지 않는다.** 수익원을 **핵심 구독·팀 확장·(비매출) 지원·미채택 모델**로 나눈 구분은 **§3-1-1**과 같다.

| 수익           | 모델                                | 타깃                                            | 시작 시점 | 예상 단가(예시)                                           |
| -------------- | ----------------------------------- | ----------------------------------------------- | --------- | --------------------------------------------------------- |
| **월·연 구독** | 무료→Pro, 저장·기능·협업(좌석) 확장 | 심화 학습·자기주도 탐구 개인, 교육·연구·제작 팀 | 4~6개월차 | 개인 월 1~3만 원대(조정 가능), 팀은 좌석·용량에 따라 협의 |

**수익 성장 경로**

```
[0~6개월]  **교수·크리에이터·전문가 소개** 초기 사용자 + 파일럿(무상·저가) → 시장 적합성·레퍼런스
    ↓
[6~12개월] **유료 구독 매출** 가속 + **선택** 공공·업무협약(검증)
    ↓
[12~24개월] 유료 사용자·**월 구독 매출** 확대
    ↓
[24개월~]  브랜드·**전문가 레퍼런스**·제품 깊이 — 구독 규모의 경제 (데이터 외판 없음)
```

**플랜(요약)**

| 플랜     | 대상    | 주요 기능                                             | 월 단가                          |
| -------- | ------- | ----------------------------------------------------- | -------------------------------- |
| **Free** | 체험    | 기본 **열람·입력**, 제한된 저장·기능                  | 0원                              |
| **Pro**  | 개인·팀 | 저장·검색·시각화·백업·협업(좌석·권한) 확장, 우선 지원 | 개인 1~3만 원대(예시), 팀은 협의 |

- **정책 수혜**: 디지털 교과서(2025~), 문화유산 디지털화 정책과 연계 — **지원·협력**으로 제품 검증·레퍼런스 확보에 유리

- **시공간 시각화**: 연대표·지도·대시보드·통계로 교육·콘텐츠 제작에 직결

**(3) 시장 진입 역량**

- **기관·분야 포지셔닝**: 교육·연구·콘텐츠·공공 등 명확한 타깃
- **정책 부합**: 디지털 교육, 문화유산 디지털화, 스마트교육 등 정부 정책과 연계

| `/history/country/:id`            | Country Detail    | 8탭(개요, 대시보드, 역대 수반, 인물, 역사적 국가, 행정구역, 행정조직, 사건) |
